# 架构与兼容边界

Deterministic Chance 面向 Minecraft 1.20.1 Forge。设计目标不是把每条概率配方写成特例，而是用一个可验证的通用数学核心，加上每个模组家族的一对薄适配层，保证 **JEI 写出的 AE2 样板** 与 **真实机器提交的结果** 使用同一组确定语义。

## 总体数据流

```text
原生配方
   ├─ JEI family adapter ─→ 精确分数/最小批次 planner ─→ AE2 pattern codec
   └─ machine commit hook ─→ per-machine sequence ───────→ 真实产物
```

每个模组适配只负责回答两件事：

1. 这族配方的原生输入、固定产物、概率产物和概率语义是什么；
2. 机器在哪一个中央位置真正提交结果，以及哪一个对象能稳定代表这台机器。

其余约分、最小公倍数、溢出检查、样板缩放、序列推进和完成周期清理全部复用核心实现。这是目前工作量最小、同时还能证明正确性的适配粒度。

## 精确批量计划

### 概率表示

核心将每个概率表示成约分后的整数分数 `numerator / denominator`，避免直接累加二进制浮点误差。原生 API 只提供 `float` 或 `double` 时，适配器会在限定分母内恢复稳定的有理数；无法安全解释的值不会进入精确计划。

若一次处理包含：

- 固定产出 `1 Ingot`；
- `50% × 2 Dust`；
- `1/3 × 1 Gem`；

所有概率分母的最小公倍数是 6，因此计划为：

```text
6 Ore → 6 Ingot + 6 Dust + 2 Gem
```

固定产物乘以执行次数；每个独立概率产物乘以该周期中的命中次数。多个产物可以拥有不同分母。

### 原生输入，不反推 JEI 槽

适配器直接读取原生配方输入，并保留每个输入槽的可替代材料列表。计划器按执行次数缩放各槽数量，再交给 AE2 样板 codec。这样不会把 JEI 为展示而轮换、合并或省略的槽位误当成配方定义，也支持多个输入、多个产物及副产物。

机器催化剂、升级、模具或工具如果不是普通消耗输入，必须由该模组适配器显式建模；不能仅因为它出现在 JEI 中就写入样板。

### 有界计划

默认最大精确执行次数是 10,000，并检查：

- 分母最小公倍数是否超限；
- 输入和输出数量是否溢出；
- AE2 样板输入/输出槽是否足够；
- 原生概率语义是否能表示成当前支持的独立输出模型。

任一检查失败都产生可解释的“不支持”结果，而不是截断、四舍五入或生成近似样板。

## JEI 三态决策

注册表对一个配方返回以下三态之一：

| 决策 | 含义 | 行为 |
| --- | --- | --- |
| `NOT_APPLICABLE` | 不属于已注册的概率配方家族 | 不干预原 JEI/AE2 流程 |
| `EXACT_PLAN` | 能生成严格整数批次 | 将原生输入和完整产物写入 AE2 |
| `RECOGNIZED_BUT_UNSUPPORTED` | 属于已知家族，但当前机器状态或配方语义无法精确表达 | 向用户显示原因并阻止错误填充 |

三态避免了最危险的失败模式：适配器已经识别一个概率配方，却因为某个边界条件返回空值，随后静默退回原来的单次 JEI 槽内容。

注册表按类名惰性加载可选适配器。对应模组缺失时不会链接其类，也不会让核心模组启动失败。

## 真实机器确定性

### 只接管提交点

仅生成 `5 → 4` 样板不足以保证 AE2 作业完成，因为原机器仍可能随机得到 3 或 5。适配器必须在机器原本的中央产物提交路径中，将一次概率判定替换为确定循环。

不在配方预览、JEI 渲染、输入可行性检查或客户端动画中推进状态。例如 Immersive Engineering 的 `canProcess` 可以预览下一结果，但只有 `processFinish` 才提交并推进。

### 每台机器持久化

序列状态属于具体机器，并以配方/有效概率配置与输出 lane 隔离。状态写入机器 NBT 或其控制器状态的 NBT，因此：

- 两台机器不会共享或抢占彼此相位；
- 保存、退出和重新载入后继续原来的循环；
- 切换配方或有效概率配置不会污染另一条序列；
- 一个分数的完整周期结束后，零相位条目会被删除，避免存档无限积累。

多方块机器的状态归属于主控制器。客户端可以预览，但只有逻辑服务端能提交相位。

### 路由约束

AE2 的一张精确批次样板，应由**同一个 provider 投入一台机器**。单机内部的批量或并行处理可由适配器按实际提交次数推进；外部物流若把一张样板的输入拆给多台拥有各自相位的机器，则不能保证这一次 AE 作业恰好收到样板声明的数量。

这是 per-machine 确定序列的自然边界。用全维度共享计数器可以掩盖这个问题，却会引入跨区块并发、机器拆除和配方切换等更难维护的耦合，因此不采用。

## 为什么不劫持全局随机数

`RandomSource.nextFloat()` 的一次调用可能属于副产物，也可能属于粒子、声音、掉落、故障或其他机制。全局拦截既无法可靠识别语义，也依赖随版本变化的调用顺序。它还缺少稳定的机器、配方和输出 lane 上下文。

所以“完全通用、零适配”的 RNG hook 不具备可验证性。本项目选择每个模组家族一个中央 commit hook；当一个家族共享执行路径时，一个 hook 就能覆盖大量配方。

## 当前适配契约

| 家族 | 机器提交范围 | JEI 精确范围 | 关键拒绝条件 |
| --- | --- | --- | --- |
| Mekanism | Precision Sawmill 与 Sawing Factory | Sawing 的固定主产物及概率副产物 | 不属于锯切家族 |
| Create | Milling 与 Crushing | 这两类 ProcessingRecipe 的原生输入和概率输出 | Fan、Basin、Manual Application、Sandpaper 等无已建模单机提交上下文的路径 |
| Thermal Series | 通用 MachineBlockEntity 输出提交路径 | 概率被配方锁定、不会随催化剂/增强变化的配方 | catalyzable、boostable 或其他依赖实际机器配置的概率 |
| GTCEu Modern 7 | 已建模的独立 `OR` 概率输出提交 | 固定数量、独立 `OR`、且所有电压 tier 下有效概率不变 | `AND`/`XOR`/`FIRST`/custom、范围数量、tick 输出、tier chance boost 或自定义等级函数 |
| Immersive Engineering | Crusher 与标准 Arc Furnace | 对应原生概率副产物；Arc Furnace 按 JSON/JEI 的概率语义处理，修正上游反向比较 | 非标准/无法稳定关联机器状态的输出语义 |
| Productive Bees | Centrifuge 的最终产物提交路径，覆盖普通、动力和加热离心机 | 多个独立 item 输出、整数 `min..max` 数量范围、固定 fluid 输出；普通/加热 JEI 输出分别建模 | 非 centrifuge 的基因瓶随机产物；它不是静态 centrifuge recipe，无法生成普通 AE2 处理样板 |
| Integrated Dynamics | Mechanical Squeezer 的非模拟最终提交路径 | 多个独立、固定数量的概率 item 输出及固定 fluid 输出 | 手动 Squeezer；覆盖 `assemble(ItemStack)`、使产物依赖运行时输入的第三方配方 |

Productive Bees 的一次范围产物不是简单取平均值。例如 `80% × 1..3` 使用 15 次完整周期：1、2、3 各命中 4 次，另 3 次不产出，总计 24。AE2 样板因此写成 15 份输入对应 24 份该产物；多个输出 lane 的周期再取最小公倍数。其正式 jar 内嵌 ProductiveLib，构建脚本只为 Loom/CI 从同一官方 jar 提取该库到本地 `.gradle` 缓存，不把第三方二进制纳入仓库。

Integrated Dynamics 的 Mechanical Squeezer 在一次处理结束时先执行模拟容量检查，再执行真正提交。适配只拦截后者的概率抽取，因此输出槽不足、模拟或取消不会消耗确定序列；状态按机器、配方和输出 lane 写入 NBT。手动 Squeezer 使用另一套玩家交互执行路径，且不是普通 AE2 机器处理目标，因此不宣称支持。

### 独立概率与互斥概率

当前通用 planner 支持多个**相互独立**的概率产物。每个产物有自己的命中序列，联合批次使用各分母的最小公倍数。

“多个结果中恰好选一个”的互斥/加权分布不能拆成几组独立布尔概率。只有适配器能把这类分布描述为一个完整互斥周期时才能支持；否则必须返回 `RECOGNIZED_BUT_UNSUPPORTED`。

## 已审计但暂缓的家族

### Create 其他处理路径

Fan 水洗/缠魂、Basin、Manual Application 与 Sandpaper 等路径目前没有纳入可持久化的单机提交上下文。对它们做全局 `ProcessingOutput` 拦截会让预览、不同机器或世界中的执行共享错误相位，因此仅支持 Milling 与 Crushing。

### Ender IO

SAG Mill 的有效概率受 Grinding Ball 等机器配置影响。JEI 的静态 recipe base 不能唯一确定玩家实际使用的球，也无法把非消耗机器状态准确表达为 AE2 普通输入，暂不生成“精确”样板。

### Industrial Foregoing

相关机制中常见的是运行时动态结果、无消耗输入、tag 中随机选取结果或方块破坏概率，而不是一个稳定统一的静态概率产物 API。当前没有足够可靠且高覆盖率的中央适配点，暂缓加入。

## 测试边界

### 自动覆盖

构建矩阵包含：

- 不加载任何可选科技模组的核心-only 启动；
- 每个可选科技模组与 AE2、JEI 的隔离组合；
- 所有已支持模组共同加载的组合。

单元测试验证约分、最小批次、溢出/上限、序列和各适配器的拒绝条件。Forge GameTest 验证可选 mixin 能随真实模组加载、真实机器结果提交与 NBT 保存恢复路径，并把生产 JEI adapter 的结果经过正式注册表送入 AE2 pattern codec 后重新解码核对。

### 不自动覆盖

dedicated GameTest 服务器没有客户端 JEI Screen，也不能真的点击 AE2 样板编码终端中的 JEI transfer 按钮。因此自动测试覆盖的是：

```text
真实 recipe / machine commit
生产 JEI adapter → 三态 registry → exact plan → AE2 codec
```

而不是完整的客户端 UI 点击端到端链路。发布前仍应执行一次客户端冒烟测试，确认按钮、错误提示与目标菜单版本的注入点正常。

## 新增适配器检查表

一个新模组家族只有满足以下条件才应标为支持：

1. 概率能映射为精确、稳定的分数，而非未知运行时状态；
2. 原生消耗输入、固定产物和每个概率产物均可读取；
3. 能区分独立、互斥、重复抽取及范围数量等语义；
4. 找到唯一的服务端结果提交点，并能得到稳定机器所有者；
5. 预览不会推进序列，失败/取消的处理不会提交相位；
6. 状态按机器、配方/有效配置和输出 lane 持久化，完整周期后清理；
7. 已识别但不支持的配方走显式拒绝，不会静默回退；
8. 至少有计划器单测、真实提交/持久化 GameTest，以及 registry → AE2 codec 验证。

这份契约比“能读到一个 chance 字段”更严格，但能让新增适配保持低维护，同时避免向玩家承诺无法成立的确定性。
